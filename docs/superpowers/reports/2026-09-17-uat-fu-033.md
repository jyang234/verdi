**F1 fix.** In both `TestRunDesignStart_ScaffoldCommitStagesOnlySpecDir`
and `TestRunDesignStartSupersede_ScaffoldCommitStagesOnlySpecDir`, added a
second, independent assertion using `gitx.StagedPaths` (index-vs-HEAD
only, `internal/gitx/stagedpaths.go` — the project's own existing,
hardened helper, already used by `addpaths_test.go`; NOT a raw `git diff
--cached --name-only`, which that helper's own doc comment documents as
fail-open under `diff.ignoreSubmodules`/`diff.relative`) and reworded the
`WorktreeChangedPaths` message to claim only what it actually proves
("an unresolved working-tree change: untracked or modified"), moving the
"never staged" claim onto the new, precise `StagedPaths` check. Extracted
the repeated three-path literal into a local `plants` slice shared by both
assertions in each test, to remove the duplication the second check would
otherwise have introduced.

Disclosed scope of this specific fix (three-valued honesty): after ANY
successful `git commit` (no `--only`/pathspec scoping, which this code
does not use), git's own invariant is index == new HEAD, so
`StagedPaths` returns empty regardless of what was staged before the
commit — meaning this assertion cannot currently distinguish "AddPaths
alone staged spec.md" from "AddPaths plus some other regression also
staged the plants, and everything staged got committed together" (that
second case is instead caught by the pre-existing `DiffNameStatus`
assertion, which already fails on any extra path in the commit tree, as
proven by this lane's original RED). What the new check adds is a direct,
independent tripwire against the narrower regression class the reviewer
named — a future rewrite that commits with a pathspec scoped to `specDir`
(e.g. `git commit -- specDir`), which would leave any OTHER staged path
sitting in the index, uncommitted, while `DiffNameStatus` against the
resulting (clean-looking) commit tree would not catch it. I did not
construct a synthetic implementation exercising that exact scoped-commit
regression to demonstrate a RED failure for this specific check, since
the current production code never scopes the commit that way; this is
disclosed rather than claimed proven.

RED/GREEN for this fix: no production behavior changed, so there is no
RED in the original sense (the pre-fix test already passed against
already-correct code); the "RED" here is that the finding named an
assertion whose message overclaimed relative to what it checked. GREEN —
run at the new head, see Recorded commands below.
